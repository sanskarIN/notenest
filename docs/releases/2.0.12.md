# NoteNest 2.0.12 Release Candidate

Status: **release candidate — not yet tagged as stable**

Package version: `2.0.12+2012`

Visible application version: `2.0.12`

Pinned Flutter SDK: `3.44.7`

Project targets: **Android, iOS/iPadOS, Windows, macOS, Linux, Web**

## Release focus

NoteNest 2.0.12 is a release-hardening milestone focused on local data integrity, deterministic async persistence, bounded file handling, strict backup validation, collection-consistent filtering, graceful failure handling, lifecycle cleanup, accessibility, external-link resilience, reproducible builds, and complete Flutter cross-platform targeting.

Core note-taking still requires no NoteNest account, project-operated note-sync backend, analytics SDK, advertising SDK, or remote note-processing service.

## Complete Flutter platform support

The 2.0.12 candidate now has an implementation/build path for all six Flutter targets:

| Target | Storage/file behavior | App-lock behavior |
|---|---|---|
| Android | Drift/SQLite + native picker/save | Device authentication where supported |
| iOS/iPadOS | Drift/SQLite + native picker/save | Device authentication where supported; Face ID usage text configured |
| Windows | Drift/SQLite + desktop picker/save | Device authentication where supported |
| macOS | Drift/SQLite + desktop picker/save | Device authentication where supported |
| Linux | Drift/SQLite + desktop picker/save | Unavailable with current `local_auth` dependency; app remains usable |
| Web | Drift SQLite WASM/worker + browser picker/download | Unavailable; browser-safe fallback keeps app usable |

This table describes implemented target behavior. Final stable verification still requires completed GitHub Actions and representative runtime/manual checks on the exact post-lockfile candidate.

### Browser database support

`AppDatabase` supplies `DriftWebOptions` pointing at:

- `sqlite3.wasm`
- `drift_worker.js`

`tool/bootstrap_platforms.py` now generates the Web runner and obtains those assets from the exact **Drift 2.34.3** GitHub release matching the direct package dependency. It validates the direct dependency pin plus basic WASM/worker payload signatures and fails if the dependency version changes without an explicit bootstrap review.

The Web deployment must preserve those generated assets. `sqlite3.wasm` must be served with the WebAssembly MIME type. Compatible cross-origin isolation can enable Drift's optimal OPFS path; otherwise tested fallback browser storage may be used. Browser note data is local to the browser profile/origin and may be removed by site-data controls, so JSON backup remains the portable recovery path.

### Browser-safe imports and exports

Shared source no longer directly imports `dart:io` for bounded file reads. The bounded reader uses conditional implementations:

- Native targets stream filesystem paths while checking reported/cumulative byte length.
- Web does not expose a fake filesystem path reader.

`FileTransferService` requests picker bytes on Web, validates the picker-reported size, then validates the actual bytes/stream accumulation before UTF-8/format processing. Native behavior remains bounded path streaming.

Limits remain:

- Markdown/text: **16 MiB**.
- JSON backup: **64 MiB**.

Markdown and JSON exports continue through `file_picker` save behavior, including browser downloads where supported.

### Safe app-lock degradation

`local_auth 3.0.2` does not implement Web or Linux. NoteNest does not invent a custom browser/Linux password or biometric substitute.

The app-lock service is now selected conditionally:

- Web uses a no-authentication implementation that reports unavailable.
- Native builds retain the `local_auth` implementation; targets without a registered implementation resolve safely to unavailable.
- The root lock gate checks capability before authentication and bypasses an impossible lock on unsupported targets.
- Settings checks capability and prevents enabling app lock when unsupported while still allowing an already-enabled stale preference to be turned off.

This prevents a persisted app-lock preference from making Web/Linux unusable.

## Major data-integrity changes

### Deterministic editor persistence

Editor writes are serialized in submission order. Debounced autosave, lifecycle saves, export/history preparation, and final navigation submissions cannot overtake one another.

Normal Back navigation waits for the current visible draft save. Failure keeps the editor open with feedback. Export/history also requires a successful current-draft save.

A stale completion cannot report a newer visible draft as saved. Missing-note initial load becomes a retryable error state.

Markdown heading/list/checklist formatting correctly handles caret offset zero when the document begins with an empty first line.

### Reliable note-browser mutations

Create/open/pin/favorite/archive/trash/restore/permanent-delete/empty-trash/undo actions contain repository failures and show concise feedback rather than leaking asynchronous exceptions.

### Reliable settings/onboarding/lifecycle ownership

Settings mutations are serialized through an injectable persistence boundary. Failed visible writes roll back when appropriate and stale failures cannot overwrite newer state.

Onboarding completion is persisted before leaving onboarding.

Dependency creation cleans up partial settings/database resources on initialization failure. Permanent root teardown delegates settings/database cleanup to `AppDependencies.dispose()`.

## Backup and import hardening

Restore validation protects:

- NoteNest application identity.
- Backup schema.
- Explicit-UTC root `exportedAt`.
- Field/list/value types.
- Serialized/canonicalized tags.
- Duplicate and whitespace-polluted identifiers.
- Version-to-note relationships.
- 32-bit ARGB color range.
- Explicit UTC note/version timestamps.
- `updatedAt >= createdAt`.
- Invalid archived+trashed or pinned+trashed lifecycle combinations.

Validation finishes before transactional restore writes and newer local note revisions win conflicts.

The live repository also rejects enabling pin state on an already-trashed note.

## Collection-consistent filtering

Folder/tag metadata follows the active lifecycle collection:

- All Notes: active/non-archived.
- Favorites: active favorites.
- Archive: archived/non-trashed.
- Trash: trashed.

Switching collections clears stale folder/tag selections.

## Cross-platform export filenames

Markdown export names normalize invalid/control characters, prohibited trailing dots/spaces, Windows reserved device names, unusable titles, excessive length, and Unicode truncation without splitting code points.

## External-link resilience

Repository, funding, business/support email, and Releases actions use `ExternalLinkService`; launcher refusal/exception becomes a safe result plus context-specific user feedback.

## Accessibility

The custom note-color selector has:

- 48 logical-pixel minimum target.
- Explicit selected semantics.
- Visible checkmark.
- Non-color reset cue.

Responsive behavior supports compact phone/browser widths and wider tablet/desktop/browser viewports. Final stable checks still require keyboard, browser focus/zoom, screen reader, large text, themes, reduced motion, and representative target review.

## Data compatibility

Drift database schema remains **version 1**. Application version 2.0.12 does not imply database schema 2. No destructive migration is intentionally introduced by this hardening.

Web uses the same logical Drift schema and FTS infrastructure through SQLite WASM. Native/browser interchange is provided through the validated JSON backup format rather than raw database-file portability.

## Privacy/security behavior

Core notes remain local to the installed application or browser origin/profile. The Web build downloads its static Flutter/worker/WASM application assets from its host; that is distinct from uploading note content. No project-operated note-sync path is required.

App lock remains UI access control, not database encryption. Unsupported targets do not gain custom credential storage.
