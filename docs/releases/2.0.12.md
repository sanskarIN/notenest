# NoteNest 2.0.12 Release Candidate

Status: **release candidate — not yet tagged as stable**

Package version: `2.0.12+2012`

Visible application version: `2.0.12`

Pinned Flutter SDK: `3.44.7`

## Release focus

NoteNest 2.0.12 is a release-hardening milestone focused on local data integrity, deterministic async persistence, bounded local file handling, strict backup validation, collection-consistent filtering, accessibility, external-link resilience, and reproducible release engineering.

The release does not add a required account, cloud backend, analytics SDK, advertising SDK, or mandatory network dependency to core note-taking.

## Major engineering changes

### Deterministic editor persistence

Editor writes are serialized in submission order. Debounced autosave, lifecycle-triggered saves, export/history actions, and final navigation/dispose submissions cannot overtake each other through concurrent repository writes.

A save completion only reports `Saved locally` when the saved draft still matches the visible editor draft.

### Reliable settings and onboarding persistence

Settings persistence now has an injectable `SettingsStore` boundary and ordered mutation queue.

For theme, text size, reduced motion, and app-lock preference changes:

- Visible state may update optimistically.
- Writes are serialized.
- A failed write propagates as a storage failure.
- If the failed value is still current, the controller restores the last successfully persisted value.
- A stale failed write does not replace a newer requested visible value.

Onboarding uses a stricter persistence-first rule: completion is written successfully before the application transitions away from onboarding. A failed write leaves onboarding visible and retryable with a user-facing error.

### Safer local imports

Markdown/text and NoteNest JSON backup imports do not request eager picker byte loading on native platforms.

NoteNest receives the picker's cached local path and reads it through `BoundedFileReader`:

- Markdown/text ceiling: 16 MiB.
- JSON backup ceiling: 64 MiB.
- Reported file length is checked before streaming.
- Every streamed chunk re-checks the active limit before being added to the final buffer.
- Filesystem failures are translated to import/export errors.
- UTF-8 decoding occurs only after the bounded read.
- Backup JSON validation occurs only after decoding.

The platform picker/provider may still perform its own caching before returning the local path, so real-platform oversized-file testing remains required.

### Stricter backup/restore validation

Restore validation includes:

- NoteNest application identity.
- Backup schema version.
- Required value types.
- Serialized tag JSON.
- Duplicate incoming note IDs.
- No surrounding whitespace in imported note/version identifiers.
- Version-to-note relationships.
- `colorValue` null or within the 32-bit ARGB integer range.
- Explicit UTC timestamps ending in `Z`.
- `updatedAt` must not precede `createdAt` for a note.

Validation completes before restore transaction writes. Restore remains transactional and preserves newer local note revisions.

### Collection-consistent filters

Folder/tag metadata now uses the same lifecycle predicate as the active collection:

- All Notes excludes Archive/Trash metadata.
- Favorites exposes only active favorite metadata.
- Archive exposes archived metadata.
- Trash exposes trashed metadata.

Switching collections clears stale folder/tag selections. This fixes the earlier behavior where Trash could contain folders/tags that were impossible to select and other collections could advertise irrelevant options.

### Cross-platform and Unicode-safe export filenames

Markdown exports:

- Normalize invalid/control filename characters.
- Trim prohibited trailing dots/spaces.
- Protect Windows reserved device names.
- Preserve Unicode.
- Limit generated basenames.
- Fall back safely for unusable titles.
- Truncate by Unicode code points rather than splitting a UTF-16 surrogate pair at the limit boundary.

### External-link resilience

Repository, funding, business-email, support-email, and release links use a centralized `ExternalLinkService`.

Launcher refusal/exception returns a controlled failure result instead of escaping into feature code. About and Settings provide user-visible feedback.

### Accessibility

The custom note-color selector uses:

- A 48 logical-pixel interaction target.
- Explicit selected semantics.
- A visible checkmark for selection.
- A non-color reset cue for the default option.

Collection empty states are context-specific so Favorites, Archive, and Trash do not offer creation/import actions whose result would be hidden by the active collection.

## Data compatibility

The current Drift database schema remains **schema version 1**. Application version 2.0.12 does not imply database schema version 2.

The 2.0.12 hardening does not intentionally introduce a destructive database migration. Existing local notes should remain compatible with the current schema. Backup schema compatibility remains independently versioned by the backup format.

A stable release must still test upgrades/opening representative fictional existing data on real supported platforms.

## Privacy/security behavior

Core note content remains local-first. NoteNest does not claim that the SQLite database is encrypted at rest. Optional app lock uses platform authentication and should not be described as database encryption.

Imported files are untrusted input. Preference storage is for non-sensitive settings, not credentials/note content. External links open only after user action. No signing secret, API credential, or real user note database belongs in the repository.
