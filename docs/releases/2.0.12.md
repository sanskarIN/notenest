# NoteNest 2.0.12 Release Candidate

Status: **release candidate — not yet tagged as stable**

Package version: `2.0.12+2012`

Visible application version: `2.0.12`

Pinned Flutter SDK: `3.44.7`

## Release focus

NoteNest 2.0.12 is a release-hardening milestone focused on local data integrity, deterministic builds, bounded local file handling, accessibility, external-link resilience, and repository/release automation.

The release does not add a required account, cloud backend, analytics SDK, advertising SDK, or mandatory network dependency to core note-taking.

## Major engineering changes

### Deterministic editor persistence

Editor writes are serialized in submission order. Debounced autosave, lifecycle-triggered saves, export/history actions, and final navigation/dispose submissions cannot overtake each other through concurrent repository writes.

A save completion only reports `Saved locally` when the saved draft still matches the visible editor draft.

### Safer local imports

Markdown/text and NoteNest JSON backup imports no longer request eager picker byte loading on native platforms.

NoteNest receives the picker's cached local path and reads it through a bounded reader:

- Markdown/text ceiling: 16 MiB.
- JSON backup ceiling: 64 MiB.
- Reported file length is checked before streaming.
- Every streamed chunk re-checks the active limit before being added to the final buffer.
- UTF-8 decoding occurs only after the bounded read.
- Backup JSON validation occurs only after decoding.

The platform file picker/provider may still perform its own caching before returning the local path, so real-platform oversized-file testing remains required.

### Backup/restore validation

Restore behavior validates:

- NoteNest application identity.
- Backup schema version.
- Required value types.
- Dates/timestamps.
- Serialized tag JSON.
- Duplicate incoming note IDs.
- Version-to-note relationships.

Restore writes are transactional and preserve newer local note revisions.

### Cross-platform export filenames

Markdown exports normalize invalid/control filename characters, trim prohibited trailing dots/spaces, protect Windows reserved device names, preserve Unicode, limit generated basenames, and fall back safely for unusable titles.

### External-link resilience

Repository, funding, business-email, support-email, and release links use a centralized safe launcher boundary.

Launcher exceptions/failures return a controlled `false` result instead of escaping into the UI. About and Settings provide user-visible failure feedback.

### Accessibility

The custom note-color selector now uses:

- A 48 logical-pixel interaction target.
- Explicit selected semantics.
- A visible checkmark for selection.
- A non-color reset cue for the default option.

Collection empty states were also corrected so Favorites, Archive, and Trash do not offer creation/import actions whose result would be hidden by the active collection.

### Reproducible toolchain

Flutter `3.44.7` is pinned consistently in:

- `.flutter-version`.
- CI quality workflow.
- Native platform build workflow.
- Release artifact workflow.

The repository also includes a version synchronization checker so the package semantic version cannot silently diverge from the version displayed in the About UI.

## Data compatibility

The current database schema remains schema version 1. The 2.0.12 release-candidate hardening does not intentionally introduce a destructive database migration.

Existing local notes should remain compatible with the current schema. Backup schema compatibility remains independently versioned by the backup format.

A stable release must still test upgrades using representative fictional existing data on real supported platforms.

## Privacy/security behavior

Core note content remains local-first. NoteNest does not claim that the SQLite database is encrypted at rest. Optional app lock uses platform authentication and should not be described as database encryption.

Imported files are untrusted input. External links only open after user action. No signing secret, API credential, or real user note database belongs in the repository.

See:

## Tagging

Only after the release candidate passes the required verification:

```bash

git push origin v2.0.12
```

Do not move a published tag to another commit. If a post-release defect requires a new build, prepare another version instead.
