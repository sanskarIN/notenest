# NoteNest 2.0.12 Release Candidate

Status: **release candidate — not yet tagged as stable**

Package version: `2.0.12+2012`

Visible application version: `2.0.12`

Pinned Flutter SDK: `3.44.7` (Dart 3.12.2)

Project targets: **Android, iOS/iPadOS, Windows, macOS, Linux, Web**

## Release focus

NoteNest 2.0.12 is a release-hardening milestone focused on:

- local data integrity;
- deterministic asynchronous persistence;
- bounded untrusted file handling;
- strict backup validation;
- collection-consistent filtering;
- graceful user-visible failure handling;
- lifecycle/resource cleanup;
- accessibility-oriented UI behavior;
- safe external-link handling;
- reproducible dependencies and build tooling;
- complete Flutter target coverage.

Core note-taking still requires no NoteNest account, project-operated note-sync backend, analytics SDK, advertising SDK, or remote note-processing service.

## Dependency and toolchain reproducibility

The release candidate pins Flutter **3.44.7** through `.flutter-version` and all maintained Flutter workflows.

A genuine resolver-generated `pubspec.lock` is now committed for the final file-picker-12 dependency graph. The lock contains **129 resolved packages**, including:

- `file_picker 12.0.0` and federated platform packages;
- `intl 0.20.2`, matching Flutter 3.44.7's localization pin;
- Drift `2.34.3` / drift_dev `2.34.5`;
- `local_auth 3.0.2` and its supported platform implementations.

CI, all six platform-build lanes, and release packaging restore dependencies with:

```bash
flutter pub get --enforce-lockfile
```

The lockfile is part of the exhaustive repository contract, which now catalogs **109 tracked files**. Repository policy also fails if the application lockfile is absent or untracked.

Ordinary development/build verification must not silently regenerate the graph. A deliberate dependency change must use the pinned toolchain, review `pubspec.yaml` plus `pubspec.lock`, and rerun affected platform verification.

## File-picker modernization

Real Android verification exposed an obsolete `file_picker 11.0.3` plugin-registration path. The 2.0.12 candidate therefore moved to **file_picker 12.0.0** rather than suppressing the Android failure.

`FileTransferService` now uses the v12 API:

- `FilePicker.pickFile()` for one selected file;
- `PlatformFile.length()` for reported-length validation;
- native cached paths through `BoundedFileReader` when available;
- `PlatformFile.readAsByteStream()` when no native path exists;
- cumulative streamed-byte validation before decoding;
- explicit MIME types for saved Markdown/JSON output.

Current ceilings remain:

- Markdown/text: **16 MiB**.
- NoteNest JSON backup: **64 MiB**.

The file-picker 12 migration also makes the project minimum **iOS 14.0+**, which the generated Xcode/framework configuration now enforces explicitly.

## Browser database support

`AppDatabase` supplies Drift Web options for:

- `sqlite3.wasm`
- `drift_worker.js`

`tool/bootstrap_platforms.py` downloads those assets from the exact **Drift 2.34.3** release matching the direct dependency. It verifies the direct Drift pin plus basic WASM/worker payload signatures and fails if the dependency/runtime pairing changes without explicit review.

The deployed Web bundle must preserve these assets. `sqlite3.wasm` must be served with the WebAssembly MIME type. Compatible cross-origin isolation can enable Drift's preferred OPFS-backed path; otherwise verify the actual fallback browser storage mode rather than assuming OPFS.

Browser note data is local to browser/profile/origin and may be removed by site-data controls. Validated JSON backup is the portable recovery path.

## Safe app-lock degradation

`local_auth 3.0.2` does not implement Web or Linux. NoteNest deliberately does not create a custom browser/Linux password or biometric substitute just to advertise parity.

- Web uses a conditional unavailable implementation.
- Native builds use `local_auth` where a platform implementation exists.
- Unsupported targets resolve capability safely to unavailable.
- The root lock gate checks capability before authentication.
- Settings prevents enabling an unavailable lock while still allowing a stale enabled preference to be disabled.

A persisted app-lock preference therefore cannot strand Web/Linux behind an impossible unlock flow.

## Data-integrity hardening

### Deterministic editor persistence

- Editor writes are serialized in submission order.
- Debounced autosave, lifecycle saves, history/export preparation, and final navigation saves cannot overtake one another.
- Every save captures an immutable draft.
- A stale completion cannot mark a newer visible draft as saved.
- Normal Back waits for the current draft save; failure keeps the editor open with feedback.
- Export/history requires the current draft to save successfully first.
- Missing-note initial load becomes a retryable local-storage error state.
- Heading/list/checklist formatting correctly handles caret offset zero on an empty first line.

### Reliable browser mutations

Create/open/pin/favorite/archive/trash/restore/permanent-delete/empty-trash/undo actions contain persistence failures and surface concise feedback instead of leaking asynchronous exceptions.

### Settings/onboarding/lifecycle

- Settings mutations are serialized.
- Applicable failed optimistic writes roll back.
- Stale failures cannot overwrite newer visible state.
- Onboarding persists before navigation leaves onboarding.
- Partial dependency bootstrap cleans up settings/database resources.
- Permanent root teardown delegates cleanup to `AppDependencies.dispose()`.

## Backup hardening

Restore validation covers:

- NoteNest application identity;
- backup schema;
- explicit-UTC root `exportedAt`;
- field/list/value types;
- serialized/canonicalized tags;
- duplicate and whitespace-polluted identifiers;
- version-to-note relationships;
- 32-bit ARGB color range;
- explicit UTC note/version timestamps;
- `updatedAt >= createdAt`;
- impossible archived+trashed and pinned+trashed states.

Validation completes before transactional restore writes. Newer local note revisions win conflicts. Live note operations also reject pinning an already-trashed note.

## Collection consistency

Folder/tag metadata follows the active collection predicate:

- All Notes: active/non-archived.
- Favorites: active favorites.
- Archive: archived/non-trashed.
- Trash: trashed.

Changing collection clears stale folder/tag selections from the previous collection.

## Cross-platform filenames

Markdown export filenames normalize invalid/control characters, prohibited trailing dots/spaces, Windows reserved device names, unusable titles, excessive length, and Unicode truncation without splitting code points.

## External-link resilience

Repository, funding, business/support email, and Releases actions use `ExternalLinkService`. Launcher refusal or exceptions become safe results plus user feedback instead of uncaught UI failures.

## Accessibility-oriented changes

The custom note-color selector includes:

- 48 logical-pixel minimum target;
- explicit selected semantics;
- visible checkmark;
- non-color reset/selection cue.

Responsive behavior supports compact phone/browser widths and wider tablet/desktop/browser viewports. Stable release still requires representative keyboard, browser focus/zoom, screen-reader, large-text, theme, reduced-motion, and device review.

## Data compatibility

Drift database schema remains **version 1**. Application 2.0.12 does not imply database schema 2. No destructive database migration is intentionally introduced.

Web uses the same logical Drift schema and FTS infrastructure through SQLite WASM. Native/browser interchange is supported through the validated JSON backup format rather than raw database-file portability.

## Privacy/security behavior

Core notes remain local to the installed application or browser origin/profile. The Web build downloads static Flutter/worker/WASM assets from its host; that is distinct from uploading note content. No project-operated note-sync path is required.

App lock remains UI access control, not database encryption. Unsupported targets do not gain custom credential storage.
