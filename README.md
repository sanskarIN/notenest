## Product principles

NoteNest is designed around a few explicit constraints:

- Core notes work locally without a NoteNest account.
- Core note content is not sent to a project-operated sync backend.
- Users explicitly choose when to import/export data or open external links.
- Browser/native differences are represented honestly instead of faked.
- Unsupported authentication capability must not make the app unusable.
- Backups are portable application interchange; raw internal database files are not the supported cross-platform interchange format.
- Reproducible releases use the committed dependency graph and pinned Flutter SDK.
- Accessibility, privacy, security, and failure handling are release requirements rather than optional polish.

## Features

### Notes and organization

- Create and edit local notes.
- Debounced automatic saving.
- Serialized writes so an older submitted autosave cannot overtake a newer draft.
- Pin and favorite notes.
- Archive, trash, restore, permanently delete, or empty trash.
- Folders, normalized tags, and optional note colors.
- Collection, folder, and tag filtering with collection-scoped metadata.
- Switching collections clears stale folder/tag filters.
- SQLite FTS5 full-text search.
- Collection-specific empty states avoid suggesting actions whose result would be hidden.

### Writing experience

- Distraction-free editor mode.
- Markdown-lite heading, emphasis, bullet, and checklist helpers.
- Correct first-line behavior even when the caret is at offset zero on an empty leading line.
- Material 3 typography and adjustable text scale.
- Immutable draft capture for each submitted save.
- Save-state feedback protected from stale completions.
- Version snapshots before changed persisted content.
- Version-history browser and restore.
- Save-before-pop, save-before-export, and save-before-history guards.

### Import, export, and recovery

NoteNest uses `file_picker 12.0.0` behind `FileTransferService`.

- Import UTF-8 Markdown, Markdown-like text, and text files.
- Native targets validate reported size and use a bounded cached filesystem path when the picker provides one.
- Browser/non-path selections validate `PlatformFile.length()` and cumulative `readAsByteStream()` bytes before decoding.
- Markdown/text import ceiling: **16 MiB**.
- NoteNest JSON backup import ceiling: **64 MiB**.
- Strict UTF-8 decoding after bounds validation.
- Export individual notes as Markdown.
- Cross-platform-safe Unicode filenames, including Windows reserved-name and trailing-dot/space protection.
- Export notes and version snapshots as human-readable JSON.
- Validate backup application identity, schema, fields, tags, IDs, relationships, UTC timestamps, timestamp order, lifecycle combinations, and 32-bit ARGB values before restore writes.
- Conflict-safe restore keeps newer local revisions.
- Restore writes are transactional.

### Settings and onboarding reliability

- Light, dark, and system appearance modes.
- Adjustable text scale.
- Reduced-motion preference.
- Optional operating-system-backed app lock where supported.
- Unsupported app-lock targets remain usable and clearly report the capability as unavailable.
- Serialized preference writes.
- Rollback after applicable persistence failures.
- Persistence-first onboarding.
- Root application teardown releases the owned settings controller and Drift database.

### Privacy and security

- No required NoteNest account for core notes.
- No required project-operated note sync.
- No analytics or advertising SDK in the core application.
- No custom cryptography claim.
- App lock is UI access control, **not SQLite database encryption**.
- Secrets and signing material are excluded from source control.
- Imports are byte-bounded before text/JSON processing.
- Backups are validated before transactional writes.
- Search values are parameterized rather than interpolated into SQL.
- Dependency restoration is lock-enforced for automated build/release evidence.
- Dedicated repository secret scan and dependency review are configured.

## Supported project targets

| Platform | Project target | Current platform design |
|---|---:|---|
| Android | ✅ Supported | Drift/SQLite, file import/export, responsive UI, device authentication where supported. Generated runner enforces minimum SDK 24, biometric permission, FragmentActivity, and AppCompat requirements. |
| iOS / iPadOS | ✅ Supported | Drift/SQLite, file import/export, Face ID usage configuration and explicit **iOS 14.0+** deployment floor. Distribution requires Apple signing/provisioning. |
| Windows | ✅ Supported | Drift/SQLite, desktop-responsive UI, file import/export, supported Windows authentication. Bootstrap includes current-MSVC compatibility required by `local_auth_windows`. |
| macOS | ✅ Supported | Drift/SQLite, desktop-responsive UI, file import/export, supported macOS authentication. Distribution may require signing/notarization. |
| Linux | ✅ Supported | Drift/SQLite, desktop-responsive UI and file import/export. Current `local_auth` dependency has no Linux implementation, so app-lock authentication reports unavailable. |
| Web | ✅ Supported | Browser-local Drift SQLite via matching WASM/worker, browser picker/download behavior, responsive UI. App-lock authentication is unavailable by design. |

“Supported project target” means the source/bootstrap/build path exists and is maintained. Stable-release certification still depends on the exact final candidate passing all automated and documented runtime checks.

## Web persistence and hosting

The Web database factory uses generated root assets:

- `sqlite3.wasm`
- `drift_worker.js`

`tool/bootstrap_platforms.py` downloads them from the **Drift 2.34.3** release matching the direct dependency and refuses to continue if the direct Drift version changes without an explicit runtime-asset review.

When deploying `build/web`:

- Serve `sqlite3.wasm` with MIME type `application/wasm`.
- Keep `drift_worker.js` and `sqlite3.wasm` reachable at the paths expected by the app.
- Verify create/edit/search, reload, browser restart, import, export, and backup behavior on the real deployment origin.
- Compatible cross-origin isolation can enable Drift's preferred OPFS-backed mode; where unavailable, verify and document the actual fallback storage mode.
- Browser data is tied to browser/profile/origin and can be removed by site-data controls. JSON backup is the portable recovery path.

## Quick start

### 1. Install prerequisites

Install Flutter **3.44.7** and the native tooling required for the platform you intend to build.

```bash
flutter --version
dart --version
flutter doctor -v
```

See [`docs/setup.md`](docs/setup.md) for host-specific prerequisites.

### 2. Clone

```bash
git clone https://github.com/sanskarIN/notenest.git
cd notenest
```

Optional local commit identity for this project:

```bash
git config user.name "Sanskar"
git config user.email "sanskarin@outlook.in"
```

### 3. Verify release/toolchain metadata

```bash
python tool/check_version_sync.py
```

### 4. Generate platform runners

```bash
python tool/bootstrap_platforms.py
```

Windows Python launcher alternative:

```powershell
py tool/bootstrap_platforms.py
```

The bootstrap generates all six Flutter runner trees with `--no-pub`, applies NoteNest's Android/iOS/Windows requirements, and prepares matching Drift Web runtime assets. Generated runners are intentionally not committed.

### 5. Restore the committed dependency graph

```bash
flutter pub get --enforce-lockfile
```

### 6. Generate Drift code

```bash
dart run build_runner build
```

Generated `*.g.dart` files are intentionally untracked.

### 7. Run

```bash
flutter devices
flutter run -d <device-id>
```

Browser example:

```bash
flutter run -d chrome
```

## Architecture overview

```text
lib/
├── app/                 # Composition root and application controllers
├── core/                # Constants, errors, logging, theme, utilities
├── data/
│   ├── database/        # Drift schema, SQLite/FTS and Web configuration
│   └── repositories/    # Notes, settings and backup persistence
├── domain/              # UI-independent filter/value models
├── features/            # About, home, notes, onboarding, settings
├── services/            # File transfer, app lock, external links
├── widgets/             # Reusable presentation controls
└── main.dart            # Application entry point
```

[`AppDependencies`](lib/app/app_dependencies.dart) owns long-lived composition and final cleanup. Repositories own persistence invariants. Services isolate plugin/platform boundaries. Controllers own application/feature state. Conditional imports prevent browser builds from importing unsupported native-only code.

Read [`docs/architecture.md`](docs/architecture.md) and [`docs/adr/`](docs/adr/).

## Data model

Drift schema version **1** contains:

- `notes` — current note state and organization/lifecycle metadata.
- `note_versions` — pre-change snapshots tied to a note with cascade deletion.
- `notes_fts` — FTS5 external-content index maintained by SQLite triggers.

Application version **2.0.12**, database schema **1**, and backup schema are separate version domains.

## Backup format

JSON backup is the supported portable interchange path. Restore validates the payload before writes and preserves newer local revisions during conflicts. Raw internal database-file portability is not promised across platforms/browser origins.

## Privacy

Core note data remains in local application/browser storage. NoteNest does not require a project-operated account or note-sync server. File import/export and external URI launches are explicit user actions.

A Web deployment necessarily serves the static Flutter/worker/WASM application assets; that is distinct from uploading note content.

Read [`PRIVACY.md`](PRIVACY.md) before distributing a modified build, especially if adding networking, telemetry, sync, accounts, AI processing, ads, or third-party data services.

## Security

- Never commit signing keys, API keys, tokens, passwords, private endpoints, `.env` secrets, or real user databases/backups.
- Treat imported files/backups as untrusted bounded input.
- Validate backup structure before database writes.
- Keep user search values parameterized.
- Keep export filenames cross-platform/Unicode safe.
- Treat preference persistence failure as real storage failure.
- Use `ExternalLinkService` instead of direct launcher calls from feature widgets.
- Use OS authentication where supported rather than storing custom credentials.
- Keep production/CI dependency restoration lock-enforced.
- Report vulnerabilities privately according to [`SECURITY.md`](SECURITY.md).

## Accessibility

The project follows accessibility-oriented engineering practices rather than claiming formal certification. It includes semantic controls, tooltips, scalable typography, theme-aware colors, touch-friendly custom controls, explicit non-color selection cues, reduced-motion support, responsive layouts, and visible failure states.

Manual keyboard, browser focus/zoom, screen-reader, large-text, compact/wide layout, light/dark theme, and reduced-motion checks remain part of stable release validation. See [`docs/accessibility.md`](docs/accessibility.md).

## Performance

Note discovery uses SQLite FTS5. Editor/settings persistence has explicit async ordering. Native imports use bounded filesystem streaming when available; browser/non-path imports enforce cumulative streamed byte limits. Browser persistence performance depends on the Drift backend available to the deployed origin/browser.

See [`docs/performance.md`](docs/performance.md).
